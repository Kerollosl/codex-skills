# AI Weekly

Kero wants a standing watch over two things happening in parallel: (1) the OpenAI and Anthropic IPOs, which he does not want to miss under any circumstance, and (2) the broader AI news/tooling landscape, which moves fast enough that a periodic digest beats him checking manually. This skill has two modes:

- **Full digest** (the default — Kero asks to run it, invokes `/ai-weekly`, or this is the weekly scheduled run): do all four sections below in order.
- **IPO-only check** (only when the invocation explicitly says to check just the IPO status and nothing else): do only Section 1, and only send a notification if something material changed.

## Execution

Resolve ordinary research ambiguity using the guidelines below. This skill does not override current permission or approval requirements. Never claim a notification was sent unless a notification tool is available and confirms success; otherwise report the finding in the digest.

Because this skill runs from fresh sessions each time (a scheduled task always starts cold, and even manual invocations may land in a different session), **do not rely on local files for state that must survive between runs.** Use the state file described in "Tracking state" below.

## Tracking state

Maintain one JSON state file in the user's Google Drive named `ai-digest-state.json`. Search Drive first. If search returns nothing, read the previously verified file at `https://drive.google.com/file/d/1aIb4NNn8T54TAQKBk_ruuvS-0MJkrpSp/view` before deciding it is absent. An empty search does not prove absence; a permission/read error is not permission to create a duplicate.

Only after absence is confirmed, create a regular JSON file in Drive with the current IPO state and the tracking maps below; initialize unobserved check timestamps to `null` and ID lists to empty.

Read the current JSON before editing and update its raw content **in place, retaining the same Drive file ID**, using the connected Drive tools. Preserve every existing field, channel, history entry, and legacy date; merge changes into a fresh read before writing so another run's IDs/history are not lost. Fetch the same ID afterward, parse the actual JSON bytes (including a base64 response when readable content is empty), and verify the changed fields and preservation of unrelated data. Do not claim persistence from an upload acknowledgment alone.

Add these per-channel maps alongside `ipo_status`, `youtube_last_checked`, `last_full_digest_run`, and all other existing fields:

```json
{
  "youtube_last_checked_at": {"PaulJLipsky": null},
  "youtube_processed_video_ids": {"PaulJLipsky": []},
  "youtube_retry_videos": {"PaulJLipsky": {}},
  "youtube_pending_good_news": {}
}
```

Initialize a key for each configured or existing channel. `youtube_last_checked_at` holds an actual scan-start UTC timestamp such as `YYYY-MM-DDTHH:MM:SSZ`, saved only after that channel's discovery and review coverage is complete. Capture it from a clock immediately before scanning that channel, not at digest completion; uploads during/after the scan remain discoverable next time. `youtube_last_checked` remains a compatible date field, never the sole deduplication mechanism. Processed IDs are append-only canonical YouTube video IDs for successfully read and accounted-for videos, including deliberate exclusions after reading. Never mark an ID processed just because it was listed, opened, title-summarized, unavailable, or failed.

Migration: keep legacy dates verbatim. Leave unknown historical UTC timestamps `null`; never convert a legacy date to a made-up midnight check or use Drive modification time as a channel check time. Backfill processed IDs only from evidence tying an observed video URL/ID and channel to successful transcript/substantive-description review (and verified delivery for Good News), recording the evidence in additive `youtube_tracking_migration` metadata. A listing/title or presumed old publication date is insufficient. Unresolved IDs stay eligible in an overlapping scan; migration alone must not advance any cutoff or `last_full_digest_run`.

Use [scripts/youtube_state.py](scripts/youtube_state.py) for deterministic migration, inclusive scan planning, and checkpoint logic; it performs no Drive/network/image actions. `migrate INPUT OUTPUT` adds missing maps without replacing legacy data. `plan STATE CHANNEL UTC_NOW CANDIDATES_JSON` returns eligible videos and staged Good News inventory. Candidate entries contain `id`, optionally `published_at` (exact UTC) or `upload_date`, and `date_certain` (true only for a verified date). Import `record_channel` to apply actual review outcomes (`reviewed`, `failed`, or `unread`); `discovery_complete=True` is permitted only after every eligible candidate is accounted for and the whole window is enumerated. Persist this returned JSON through Drive and read it back. A migration/logic test uses fixture files only.

`youtube_retry_videos[channel][video_id]` retains the source URL, failure/unread status, reason, and known upload metadata. Retry these IDs regardless of age or whether they still appear in the newest listing, and remove them only after successful review. Successful IDs may be checkpointed even when another video fails; keep that channel's prior cutoff while coverage is incomplete. For Good News, store successfully read videos' complete item inventories and source URLs under `youtube_pending_good_news[video_id]` until the infographic is verified and delivered; this avoids re-reading them when retrying a failed video or image. These staged IDs skip transcript review but remain part of the pending delivery, never disappear from its inventory.

If Drive tools are unavailable, report the tracking limitation, use a 7-day lookback, and do not claim an update. Exact IDs are the deduplication authority; timestamps only narrow discovery. Format-only image tests leave **all tracking fields unchanged**, including IDs, retry queues, inventories, and run timestamps. IPO-only runs do not advance YouTube tracking. Advance `last_full_digest_run` only after the real full digest is delivered; partial attempts may update attempt metadata without implying complete coverage.

## Section 1 — OpenAI / Anthropic IPO watch

The goal is zero chance of missing either listing, so treat "no news" as a valid, boring outcome. Do the full research (steps 1-4) every run — the depth doesn't change — but Kero has explicitly said the *report* on this section was too verbose and too much play-by-play. He does not want to know what you searched, which trackers loaded, or that you double-checked EDGAR. He wants exactly two things, stated plainly: **(a) has either company actually IPO'd or gone imminent, yes or no**, and **(b) is there any genuinely notable adjacent news worth his time.** Everything else — the research trail, confirmation that nothing changed, restated background on prior filings — stays out of what Kero sees. Keep the full detail in the state file for your own comparison purposes; don't put it in his report.

1. Use the available web search tool to run a fresh search for each of "openai IPO date announced," "openai stock ticker S-1," "anthropic IPO date announced," and "anthropic stock ticker S-1" (don't reuse Kero's old Google search links verbatim — they're stale search-result URLs, not live sources; searching fresh each time is what actually matters). Prioritize the last 30 days of results. **Lead with search, not direct fetch** — WebFetch on a fresh/unapproved domain can require interactive approval that isn't available during an unattended scheduled run, so treat direct fetches as a nice-to-have, not the primary path.
2. Also try opening both tracker pages, `https://ipos.fyi/tracker/openai-ipo` and `https://ipos.fyi/tracker/anthropic-ipo` — they're purpose-built and worth the extra detail when the fetch goes through. If a fetch stalls or is blocked (provenance/approval gate, timeout, etc.), don't let it hold up the rest of the run: skip it and rely on the search results instead.
3. Compare what you find against `ipo_status` in the state file for each company, purely to decide whether to alert — this comparison is internal bookkeeping, not something to narrate to Kero.
   - **Neither company has gone public and neither is imminent** (still no listing date, no ticker, no roadshow-complete signal) → this is the default, boring case. Report it in a single line: a plain "No — neither has IPO'd or is imminent" plus, only if something is genuinely new and useful (a fresh filing, a credible date from a primary source, a notable secondary-market development), one line of adjacent news. If there's truly nothing new, that one "still no" line is the entire section. In the IPO-only run, do NOT send a push notification for this case — just replace the state file and end.
   - **Something material changed** — an S-1 went public/non-confidential, a listing date was set, a ticker was assigned, trading actually opened, or credible reporting from the company itself (not a speculative tracker) that retail access is imminent — lead with that fact directly ("Yes — \<company\> is now trading" / "Yes — \<company\> set a listing date of X"). In a full digest this is the headline item. Send a push notification either way (full digest or IPO-only run) so Kero doesn't have to open the session to learn it, and replace the state file with the new summary.
4. Use your judgment on extra sources — e.g. SEC EDGAR full-text search for "OpenAI"/"Anthropic" S-1 or F-1 filings if the tracker sites seem thin, since an actual SEC filing is the most authoritative possible signal. This is research depth, not something to describe in the output.

## Section 3 — YouTube channel transcript sweep

Channels: `https://www.youtube.com/@PaulJLipsky`, `https://www.youtube.com/@Chase-H-AI`, `https://www.youtube.com/@GoogleDevelopers`, `https://www.youtube.com/@OpenAI`, `https://www.youtube.com/@claude`, `https://www.youtube.com/@NikiasMolina`, `https://www.youtube.com/@Good__News` (special handling below).

1. Capture each channel's actual scan-start UTC time. Enumerate its Videos tab sorted by newest, plus Shorts for Good News. Use an **inclusive overlapping upload-date window**: from the UTC calendar date of `youtube_last_checked_at` minus two days, or the legacy `youtube_last_checked` date minus two days when the exact timestamp is unknown; use the last 7 days only when neither exists. Include the whole boundary day and every later day, even when the last check was earlier today. Resolve relative/local dates on the watch page when needed; uncertain or missing dates remain candidates. Load enough results to cover the full window; stop only at confidently older uploads, accounting for pinned/out-of-order entries. Persist unread candidates before ending a partial scan. 2. Capture canonical IDs from observed watch/Shorts URLs and deduplicate by ID. Skip IDs already in `youtube_processed_video_ids[channel]`, and reuse persisted Good News inventories for IDs in `youtube_pending_good_news`; do not reread either. Add outstanding retry IDs even if their dates fall outside the overlap. For each remaining eligible video, pull the transcript (YouTube's own transcript panel — expand the description with "...more" first, then "Show transcript" becomes clickable) and actually read it, or read the fully-expanded description when it's genuinely substantive (common for short official-announcement clips that state the real news — benchmarks, pricing, availability — directly in the description). 3. For the AI/technology channels (all channels except `Good__News`), write a concise, insight-dense summary per channel: skip pure filler/vlog content, and for anything substantive call out what's actually new (a capability, a technique, a product) rather than restating the video's framing. If a channel has zero new videos, say so in one line — don't pad. When multiple channels are covering the same underlying news (e.g. several reacting to the same model launch), synthesize it once instead of repeating it per channel.
4. When a video covers a major development Kero may want to explore further — for example, a significant model or product launch, a substantial capability leap, a major pricing/access change, or a practical technique that could materially improve his workflow — include a descriptive Markdown link to that specific video alongside the finding, plus a short explanation of why it matters. Judge significance from the transcript or substantive description, not a sensational title. Capture the actual video URL while reviewing it; never invent a video ID or substitute a channel link. Add a timestamp link to the relevant segment when the transcript provides a reliable timestamp. If several videos cover the same major development, keep the synthesized summary and link the most informative source video (additional videos only when they add distinct value). Ordinary updates can remain concise without extra video links.
5. Checkpoint successfully reviewed AI/technology IDs and persist unread/failed IDs for retry. Advance that channel's `youtube_last_checked_at` to the captured scan-start UTC time, and its legacy date to that time's UTC date, only when discovery covered the full inclusive window and every eligible/retry video was successfully read and accounted for. A failed video must never enter the processed list. Leave other channels' state unchanged; a channel listing failure or unresolved date boundary is incomplete coverage. Good News also has the delivery gate below.

Do not apply the AI relevance filter, major-development threshold, or a top-items limit to this channel.

Under `### Good News` inside `## YouTube Roundup`, deliver a generated infographic image instead of a written news list. Omit introductions, commentary, video-by-video summaries, and filler. Distinguish upload dates from event dates; label the digest date and reviewed upload window without implying every event happened during that window.

Give the tool the exact approved copy for every item and require each item exactly once. Use a clear title, large high-contrast text, compact numbered cards, and small relevant illustrations; warm ivory with forest-green, teal, and ochre accents is the tested default. Let the number of items determine the layout. A two-column portrait image worked for 22 items; use additional images when necessary for readability, never a top-items limit or omitted stories. Inspect the generated image against the full inventory before delivering it: check every item's presence, wording, numbers, qualifiers, and legibility. If no items are found, write “No new good-news items since the last check.” without generating an empty infographic. If image generation is unavailable or fails, report that limitation rather than claiming the image was delivered, and preserve the prior Good News cutoff for a retry. For an explicitly requested format-only test, reuse the already-reviewed items from the conversation, generate only the Good News image, and leave Drive tracking state unchanged.

Commit staged Good News IDs to `youtube_processed_video_ids.Good__News`, clear only the delivered pending inventories, and advance its exact UTC/legacy checkpoints only after all eligible/retry uploads were successfully read and every distinct item was verified and delivered in the infographic (or a verified no-item result). ## Output format

Use markdown headings for each section (`## IPO Watch`, `## GitHub / skills.sh`, `## YouTube Roundup`, `## Cockpit`) in that order, with bullet points under each — not paragraphs of prose. The `### Good News` subsection uses the infographic image and source links described above instead of story bullets. Kero has explicitly said the report was too wordy and hard to scan; simplified structure is the standard now. Don't repeat background he already knows (e.g. don't re-explain what an S-1 is).

**IPO Watch must be the shortest section.** Lead with the direct yes/no ("No — neither has IPO'd or is imminent") as the first bullet, then adjacent news only if it clears a real bar. Never narrate the research process itself (what was searched, which tracker sites were tried, whether EDGAR was checked) — keep it to the finding, not the method.

For an IPO-only check (rare — only when explicitly requested, since the scheduled task now runs the full digest by default), there's no reply to format the same way — the deliverable is the push notification (only sent when something changed) plus the updated state file, following the same discipline: lead with the yes/no fact, not a description of what was checked.
